# Планировщик задач для Битрикс24 — контекст проекта

Этот файл читается Claude Code автоматически. Он даёт всё необходимое, чтобы
продолжить работу над проектом в новой сессии (в т.ч. на другом аккаунте):
архитектуру, как деплоить, где что лежит и какие есть подводные камни.

## Что это

Недельный планировщик (ПН–ПТ, сетка 8:00–18:00, шаг 30 мин) для сотрудников
портала Битрикс24. Встраивается в портал как placement-приложение и размещается
на хостинге **vibecode** (Bitrix24 VibeCode). Показывает по сотрудникам события
календаря и вручную запланированные задачи; считает часы задач (план/факт/сегодня).

Портал: **avrika.bitrix24.ru**. Приложение: **app-x6tctp** («Ключ для планировщика»).

## Ключевая архитектура (важно!)

Vibecode встраивает приложения по **BFF-схеме**, а НЕ через классический
`BX24.callMethod`:

- Шлюз открывает приложение через `/v1/bitrix-handler`, авторизует пользователя
  и на каждый запрос к серверу приложения подставляет заголовок
  `X-Vibe-Authorization: Bearer vibe_session_*` (в браузер токен не попадает).
- Поэтому фронтенд НЕ ходит в Битрикс24 напрямую, а обращается к собственному
  бэкенду `server/bff.py`, который проксирует REST vibecode (`/v1/*`),
  добавляя `X-Api-Key` (ключ приложения, серверный секрет) ВМЕСТЕ с
  `Authorization` из сессии шлюза. Без обоих заголовков `/v1/*` даёт `INVALID_API_KEY`.
- Старый путь через `//api.bitrix24.com/api/v1/` (BX24 JS SDK) на этом хостинге
  НЕ работает — не пытайтесь его вернуть.

Поля ответов vibecode обычно в **camelCase** (`id`, `lastName`, `timeEstimate`,
`timeSpentInLogs`). НЕ передавайте `select` с UPPER_CASE-именами — вернётся
только `id`. Проще брать полные записи и мапить с запасными вариантами.

## Структура кода

- `index.html` — оболочка (BX24 SDK удалён намеренно).
- `js/config.js` — GRID, COLORS, TASK_STATUS, apiBase (`/api/v1`).
- `js/b24.js` — транспорт: `init` (проверка сессии через `/api/whoami`),
  `apiGet`/`apiSend` (в `/api/v1/*`), `bffRequest` (собственные эндпоинты BFF),
  `getOption/setOption` (localStorage), `loadPortalDomain`.
- `js/data.js` — доменный слой: пользователи, события, размещения задач, часы.
- `js/dates.js` — даты/время, `formatHM` (Ч:ММ).
- `js/state.js` — состояние (allUsers, selectedUserIds, portalDomain, dataByUser).
- `js/ui/calendar.js` — сетка, блоки, resize за края, Shift+ЛКМ копирование,
  ссылка на задачу по клику на название.
- `js/ui/modals.js` — попапы: слот-меню, форма задачи, форма события (тип
  Встреча/Отсутствие), выбор существующей задачи, форма размещения.
- `js/ui/employees.js` — мультиселект сотрудников + попап настроек (шестерёнка).
- `js/ui/tooltip.js`, `js/ui/toast.js` — тултип и уведомления.
- `css/styles.css` — стили.
- `tools/build-singlefile.mjs` — сборка всех модулей+CSS в один `dist/index.html`.
  Правьте исходники в `js/`/`css/`, затем пересобирайте — деплоится именно
  `dist/index.html`.
- `server/bff.py` — BFF-сервер (раздаёт статику + прокси + хранилище размещений).
- `scripts/` — деплой и управление сервером (см. ниже).

## Как деплоить

Нужны `node`, `python3`, `curl` и переменная окружения `VIBE_APP_KEY`
(ключ приложения `vibe_app_local_...`).

```
export VIBE_APP_KEY='vibe_app_local_...'   # секрет, см. раздел «Секреты»
sh scripts/deploy.sh                        # сборка + загрузка + рестарт + проверка
```

Прочие скрипты (все читают VIBE_APP_KEY и scripts/env.sh):
- `scripts/exec.sh "<команда>"` — выполнить команду на сервере.
- `scripts/upload.sh <local> <remote>` — загрузить файл.
- `scripts/wake.sh` — дождаться пробуждения сервера (будит, если спит).

Параметры (несекретные) — в `scripts/env.sh`:
SERVER_ID=`108d2440-8546-4c0a-a0c8-d6c6f1ed07c7`, GATEWAY=`https://vibecode.bitrix24.tech`,
APP_URL=`https://app-13995b2c41ce.vibecode.bitrix24.tech`, PORTAL=`avrika.bitrix24.ru`.

На сервере: сервис `planner.service` (systemd), файлы в `/opt/app`
(статика `/opt/app/public`, `bff.py`, `keepawake.sh`, данные `/opt/app/data`).
Ключ приложения хранится в юните `planner.service` (env `VIBE_APP_KEY`) —
при апдейте только `bff.py`/`index.html` рестарт юнита ключ не теряет.

## Данные и поведение

- **Сотрудники**: `GET /v1/users` (camelCase). Автоматически подтягиваются в
  попап настроек.
- **События календаря** (встречи/отсутствия): грузятся АВТОМАТИЧЕСКИ
  (`GET /v1/calendar-events?type=user&ownerId=..&from=..&to=..`). Создание/апдейт
  требует `from`/`to` (не `dateFrom`/`dateTo`) — шлём оба.
- **Задачи в планировщик автоматически НЕ ставятся.** Только вручную: пользователь
  кликает по ячейке и создаёт задачу или выбирает существующую. Выбор существующей
  создаёт «размещение» (см. ниже), саму задачу не меняет.
- **Размещения задач** (планирование): общее серверное хранилище BFF
  `GET/POST/PATCH/DELETE /api/placements` (файл `/opt/app/data/placements.json`,
  атомарная запись под локом). Видны всем пользователям портала. Часы/статус
  подтягиваются у задачи по `taskId` (`GET /v1/tasks/:id` + `/tasks/:id/time`).
- **Часы** ф/п/с считаются в секундах и выводятся как Ч:ММ (`formatHM`).
- **Клик по названию** размещённой задачи открывает её карточку:
  `https://<portal>/company/personal/user/<uid>/tasks/task/view/<taskId>/`.
  Домен портала отдаёт BFF: `GET /api/portal` (кэш через `/v1/me` по ключу).
- **Shift+ЛКМ** по ячейке — перетащить КОПИЮ в другую ячейку.
- **Resize** ячеек (размещения/события) — тянуть за верх/низ; шаг 30 мин.
- **Корзина** у ячейки: размещение убирается локально; событие/задача удаляются
  из Битрикс24 с подтверждением.

## «Не засыпать» в рабочее время

Сервер спит после 60 мин простоя. Настроено бодрствование ПН–ПТ 09:00–18:00 МСК:
1. Wake-schedule платформы: `POST /v1/infra/servers/:id/wake-schedules`
   `{cronExpr:"0,30 9-18 * * 1-5", timezone:"Europe/Moscow"}` (будит спящий сервер).
2. In-VM keep-alive: `/opt/app/keepawake.sh` + `/etc/cron.d/planner-keepawake`
   (каждые 20 мин делает аутентифицированный запрос → активность).
Подробности — в `server/README.md`. VM переведена в Europe/Moscow.

## Тестирование без портала

Реальную сессию портала выдаёт только Битрикс24. Для проверки полного пути
(шлюз → BFF → /v1) можно минтить временный токен:
```
POST /v1/infra/servers/:id/access-tokens {"mode":"api-bearer"}
# затем: Authorization: Bearer <token> на https://app-....vibecode.bitrix24.tech/...
```
Он проверяет путь и собственные эндпоинты BFF (`/api/placements`, `/api/whoami`,
`/api/portal`), но НЕ авторизует `/v1/*` (там нужна настоящая vibe_session).
Диагностика на сервере: временно включить лог в bff.py (env `BFF_DEBUG=1`,
файл `/opt/app/bff.log`) — сейчас выключен.

## Секреты и безопасность

- Ключ `vibe_app_local_...` — секрет. В коде фронтенда его больше нет, но он
  ОСТАЛСЯ В ИСТОРИИ git (ранние коммиты `js/config.js`) и лежит на сервере
  (юнит `planner.service`, `keepawake.sh`). Рекомендуется перевыпустить.
- В новой сессии задайте ключ переменной окружения `VIBE_APP_KEY` (в настройках
  окружения Claude Code как секрет, либо `export` перед `scripts/deploy.sh`).
  В репозиторий ключ не коммитить.
